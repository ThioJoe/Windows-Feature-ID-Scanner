# Windows-Feature-ID-Scanner
A modern take on mach2's feature scanning: GitHub Actions scans Windows 11 for feature IDs and their names (ARM64 on a GitHub runner, x64 in a virtual machine built from Microsoft's servers), stores the results per build, and tracks what changes between builds.

**Browse the data:** the GitHub Pages site (published from `site/`) compares any two scanned builds (added / removed / renamed features, feature store changes, default state changes, and the shell folders, settings pages, Settings search entries, URL protocols and other links Super God Mode found in each) and lists every feature ID in a build with the build it first appeared in. Click a feature to see what its code reveals: the functions that check it, the strings they use, its default state, and the chain of features it requires with their default states (a feature that's on by default stays off if one of them is off), with a button that copies its ID and theirs as a list for ViVeTool, and, where a feature trace saw it checked while Windows ran, the processes that checked it and the pages, folders or apps it was checked for. It also lists the builds Microsoft has released for every Windows 11 version and Insider channel, and which of them have been scanned.

## How it works

The `Windows Feature Scanner` workflow (`.github/workflows/windows-scanner.yml`) runs on the `windows-11-arm` runner, because the Windows Server images don't carry the consumer feature set.

1. **`scan-symbols.py`** finds feature names and IDs in Microsoft's public symbols. For every binary under the Windows directories it downloads the matching PDB from the Microsoft symbol server and reads the symbols that WIL feature staging emits (`Feature_<Name>__descriptor`, `Feature_<Name>__private_descriptor`, `__WilFeatureTraits_Feature_<Name>::id`), then reads each feature's ID from the binary. C++ features in binaries built with older WIL have no descriptor; their ID comes from the code of their `GetCurrentFeatureEnabledState`, which passes it to Windows. This replaces mach2, which is retired and fails on current PDBs. For binaries that contain features, it also analyzes their code (see below). It also scans the binaries of the component store (WinSxS), the newest version of each component (`--component-store`): the files of optional features that aren't turned on, such as Hyper-V and the Windows Subsystem for Linux, of components that only live there, such as the servicing stack, and of installed ones outside the folders above, such as the driver store's drivers for hardware the machine doesn't have. Binaries already found in those folders are the same files, so their PDBs aren't read twice. Windows keeps the files of components that aren't installed compressed (LZMS blocks, or a delta against nothing); they're expanded with Windows' own `cabinet.dll` and `msdelta.dll`. A build lists the modules only the component store has in `componentStore`, and the site says so in a feature's details.
2. **`scan-features.ps1`** runs ViVeTool to dump the feature store (the IDs actually configured on the machine) and fills in names from step 1.
3. **`run-super-god-mode.ps1`** runs the latest release of [Super God Mode](https://github.com/ThioJoe/Windows-Super-God-Mode) and keeps its statistics: CSV files listing the build's CLSID shell folders, named special folders, task links, `ms-settings:` pages, deep links, URL protocols and hidden app links, and the XML data the task links and deep links come from. The shortcuts it creates aren't kept. If it fails, the scan carries on without its statistics.
4. **`trace-features.ps1`** records which features Windows' code checks while it runs, while it opens the shell's UI, the Start menu's apps and the pages and folders Super God Mode found (see [Feature traces](#feature-traces)). If it fails, the scan carries on without a trace.
5. **`update-data.py`** puts all of it in the build's folder, `data/builds/<build>-<arch>/`, with the update the build came in (e.g. 2026-08 B), its release date and KB article from the list of released builds, and regenerates the index, first-seen table and diffs. The workflow commits the result and republishes the site.

The workflow runs daily: a small check job reads the runner's Windows build and only starts a full scan when that build isn't in `data/` yet. It can also be started manually from the Actions tab, which always scans.

Scanning downloads several GB of PDBs (each is deleted after reading). What was found in each PDB is stored in `data/symbol-cache.json` (`data/symbol-cache-AMD64.json` for the x64 scans), keyed by the PDB's name and GUID, so later scans only download PDBs for binaries that changed. PDBs the symbol server doesn't have (404) are remembered too and re-checked after 14 days. The cache keeps the PDBs that builds still need: those of the builds the symbol catch-up still checks (see below) and those of the newest build of each base build number, so Insider builds, which have thousands of PDBs no other build has, don't keep making it bigger. If a changed binary's PDB still can't be downloaded after retries, or the symbol server doesn't have it (Microsoft can publish an update's symbols days after the update), the scan uses what the newest earlier version of that binary contained and marks those features `"unverified"`, rather than dropping them. Earlier means from that build or one before it, by the first build each PDB in the cache was seen in, so a released build never gets an Insider build's newer code this way. A PDB that was read before keeps its features even if it can't be downloaded again. Scanning a build again adds to its data and never removes anything: a feature, name, module, code detail or feature store configuration that only the earlier scan found is kept (symbols that can't be downloaded any more, a Store app version the new VM doesn't have, a feature store entry that isn't there today), and where both scans have a value, the new one is kept. The exception is a feature marked unverified, known only from an earlier version of a binary: it's replaced by what the binary's own symbols say once a scan reads them. Super God Mode statistics are replaced too, unless the new run produced none.

Microsoft can publish an update's symbols days after the update: the x64 symbols of most binaries KB5132061 changed went up three days after its release, after the VM had scanned its builds. So each scan also lists the build's PDBs in its folder (`symbols.json`), each with what's needed to download its binaries from the symbol server, which keeps binaries by file name, PE timestamp and image size, and marks the ones it got no verified data for. With every binary listed, a build's symbol data can also be made again later without a VM, for example after a change to the analysis. Every day, the `Symbol Catch-up` workflow (`.github/workflows/symbol-catch-up.yml`, `catch-up-symbols.py`) asks the symbol server for those PDBs, for 60 days after a build's release (14 for an Insider build, which the channel's next build replaces). When it has some of them now, a Windows runner scans them without a VM (`scan-symbols.py --manifest`: their binaries come from the symbol server and have to match the SHA-256 the scan recorded) and adds them to the build with `update-data.py`, which keeps the build's feature store data and Super God Mode statistics. Until then, the site shows a notice on the build and its comparisons, and a scan that didn't get the symbols of more than a few binaries with features gets a warning on its run.

## x64 builds in a virtual machine

The `Windows VM Feature Scanner` workflow (`.github/workflows/windows-vm-scanner.yml`) scans x64 builds of Windows 11 regardless of what runner images exist. GitHub's x64 runners run Windows Server, but they can run Hyper-V virtual machines, so `scan-in-vm.ps1` builds a Windows 11 Enterprise VM on one, entirely from Microsoft's servers:

1. The base image comes from the Media Creation Tool's catalogs of Windows images, which list each image file on Microsoft's servers with its hash. The tool's download link still points to a 24H2 catalog from June 2025; the tool then asks Windows Update's metadata service for the current catalog (26H2 at the time of writing), and so does the script. It takes the newest image that can become the target version: a 26H2 image can't become 25H2, so 25H2 and 24H2 start from the 24H2 one. The image is applied to a virtual disk that boots without the setup screens.
2. The target cumulative update, from the Microsoft Update Catalog, is installed inside the running VM with DISM. 24H2, 25H2 and 26H2 share their code and their cumulative updates.
3. Unless the image is that version already, the target version's enablement package is installed, which is what makes the build a 25H2 or 26H2 one. Microsoft distributes it only through Windows Update and WSUS, not the Update Catalog. The runner is a Windows Server, so it sets up the WSUS role in the background and synchronizes Windows 11's upgrades, which gives the package's file on Microsoft's servers; the VM installs that file alone with DISM, which keeps the build at the target update. Failing that, the VM takes the file from Windows Update's offer of the version (chosen with its target release version policy), which it only downloads, since the offer comes with the newest cumulative update. Windows Update doesn't offer the version every time; the VM then gets the file with the newest update installed, and goes back to a checkpoint taken before. That's what lets any past build be scanned, not only the newest.
4. Windows Update then installs whatever else it offers, as it would on any PC at that build (Defender and Windows Security platform updates, .NET and so on), leaving out updates that would change the build. The Microsoft Store updates the apps that come with Windows, which cumulative updates don't touch, so they're at the versions a PC gets today rather than the ones the image was made with. An app update that fails because the app is running is retried after closing what Windows' deployment log names, and whatever still fails is retried after a restart. Apps and these other updates don't decide the build, so one that still can't be installed doesn't stop the scan; the build's data gets a `notes` entry saying so.
5. After a last restart, the VM is checked against what the build is supposed to be:
   - Windows' servicing lists the build's cumulative update as installed, with no update half installed or waiting for a restart.
   - `DISM /ScanHealth` and `sfc /verifyonly` find no file that differs from the component manifests Microsoft signs.
   - `verify-windows-files.py` checks the installed files against Microsoft's own lists. Each update's KB article (read through the Microsoft Learn API, see below) links a file list with the name, version and SHA-256 of every file the update carries. Every file installed from Windows' component store has to be either a file one of the installed updates lists (by SHA-256) or exactly the file in Microsoft's image the VM started from, listed right after the image is applied. Which of an update's components apply to a system is decided by Windows' servicing, which the first check covers.

   If a check fails, nothing is recorded. The reports (`verification.json` and the others, plus a list of every file with its SHA-256) are kept with the run's artifacts either way.
6. The same scan as on the ARM64 runner runs inside the VM, with Super God Mode run as the VM's own user, as it would be by someone using that PC. If the VM didn't end up at the expected build, nothing is recorded. Then the VM restarts for the feature trace, which records from boot on, so boot and sign-in are in it.

Starting from an older image and updating it gives the same Windows as Microsoft's own image of that build: built both ways (from Microsoft's 26300.9711 image as it is, and from the June 2025 24H2 image plus the October update and the 26H2 enablement package), every file installed from the component store was byte-identical between the two VMs, and neither had one the other lacked, apart from three of .NET's precompiled native images. The differences were in apps (the Store apps and Edge an image comes with), the update history, and files Windows generates on each PC.

A daily check (`check-windows-builds.py`) finds the builds Microsoft has released for every Windows 11 version and every Windows Insider channel. It starts a scan for each build of 26H2, 25H2 and 24H2 (the versions the VM can be built for) that is newer than the newest build of that version in `data/`, so no build is missed when two come out between checks (the newest three, if more are missing). A version with no build in `data/` yet starts at its newest. It also starts a scan for the newest build of each Insider channel except Release Preview (see below), unless the repository variable `INSIDER_SCANS` is `false`. Monthly security updates, optional previews and out-of-band releases all count, since each is a different build. The sources are Microsoft's, read on every check and compared with each other:

- **Versions and their updates:** support.microsoft.com's index of its Windows 11 update history (JSON), checked against the [Windows 11 release information](https://learn.microsoft.com/en-us/windows/release-health/windows11-release-information) page, which also stands in for the index when that can't be read.
- **Insider builds:** the index of the [Windows Insider release notes](https://learn.microsoft.com/en-us/windows-insider/) (JSON), with each build's release date from [Flight Hub](https://learn.microsoft.com/en-us/windows-insider/flight-hub/), which also stands in for the index.
- **Pages:** KB articles, the release information page and Flight Hub are read through the [Microsoft Learn API](https://learn.microsoft.com/api/mcp) (`microsoft_learn.py`), which gives a page as Markdown. A page's HTML is only read when that fails.

The builds a run scans are scanned at the same time, each on its own runner. Once they've all finished or failed, one job adds the ones that were scanned to `data/` in a single commit, oldest first (a build's missing feature names are filled in from earlier builds, including in builds already in `data/` when an earlier build is added after them), and merges their symbol caches (`merge-symbol-caches.py`), keeping usage details for the PDBs of the builds it scanned as far as the file stays under 90 MB (GitHub refuses files over 100 MB).

A source that fails, or two that disagree, show up as warnings on the run. The run's summary lists the newest builds of every version and channel; the list is kept in `data/releases.json` and shown on the site. 26H1 isn't scanned: it's a separate branch for new devices, and the Media Creation Tool's catalogs have no image of it.

Insider builds are scanned in the VM too. Windows Update gives an Insider channel's newest build to a request that describes a device in that channel, without anything being enrolled or signed in. `windows_update.py` makes the requests Windows' own update client makes (Microsoft's Windows Update protocol: `GetCookie`, `SyncUpdates`, `GetExtendedUpdateInfo2`) and gets the update's files, each checked against the SHA-256 in its metadata. The update is the whole build, in every language and edition (about 100 GB), and its `AggregatedMetadata.cab` has the component databases that say what each file is. A released build's image can't be updated to an Insider build: the channels' cumulative updates are built on the channels' own baseline (`ge_release_flt` 26100.6, not 26100.1), which is why Microsoft's docs say a device joins a channel by an in-place upgrade. So for `scan-in-vm.ps1 -InsiderChannel <channel>`, the VM is made from the build's own installation image instead of the Media Creation Tool's: the Pro image (`professional_en-us.esd`), applied with DISM together with the files it refers to (in the update's package ESDs and WIMs, and in the cabs of the features an installation has, unpacked with `expand.exe` and captured into one WIM), then made Enterprise with `DISM /Set-Edition`. The apps that come with Windows are separate packages in the update: the ones the edition's component database names (for Pro, 47 in the Beta and Experimental builds, the same apps the Media Creation Tool's Enterprise image has, and 50 in the 26H1 and Future Platforms builds) are provisioned in the image with DISM, each with the frameworks it requires and its license from the app database (`DesktopTargetCompDB_App_Neutral`). The VM then installs the build's cumulative update, the checkpoint cumulative update it builds on, the enablement package that gives the build the channel's build number, and the .NET Framework update, with DISM. A Future Platforms build is a whole build, without a cumulative update: its image is the build already, so only the .NET Framework update is installed. Insider builds are signed with Microsoft's development certificates, so flight signing is on, as on any Insider PC and as Microsoft documents for Insider builds (`bcdedit /set flightsigning on`); nothing else about the VM is changed, and it isn't enrolled in the program. The checks then run without the file check, since Insider builds have no file lists. After its first start, a Future Platforms build runs eBPF's files (`ebpfapi.dll` and five others) as the `_preview` variants it has next to them, which sfc reports as different from the component store; the check accepts a file that's the same as its `_preview` variant, when sfc doesn't flag that variant. This has been tried with Beta, Experimental, Experimental (26H1) and Experimental (Future Platforms). Windows Update only gives a channel's newest build, so that's the one the daily check scans: a build that comes out and is replaced between two checks isn't scanned. Release Preview's builds are scanned as the updates they become.

A scan of one build takes about an hour to an hour and a half on GitHub's runner. Since 25H2 and 26H2 start from different images, a comparison between them can also show differences in the apps the images come with: the Store doesn't bring every app on an older image to the version a newer image has. Manual runs can pick the versions, scan specific builds (older ones, for example) and rescan builds that are already in `data/`. (Microsoft's ISO download page turns away requests from GitHub's runners, so the base image comes from the Media Creation Tool's catalog instead.)

## Feature traces

Each time Windows' code checks a feature, Windows can write an event: the `Microsoft-Windows-FeatureConfiguration` ETW provider (`{c2f36562-a1e4-4bc3-a6f6-01a7adb643e8}`, with its manifest in `fcon.dll`) has an event for each stage a feature can be compiled with (1007 always disabled, 1008 disabled by default, 1009 enabled by default, 1010 always enabled), which gives the feature's ID and how the check came out (its `Kind`: on or off, and the variant of a variant check, as Microsoft's own StagingTool decodes it). The event header gives the process. A feature only shows up if code that checks it runs while the trace records, so `trace-features.ps1` makes Windows run as much of that code as it can:

1. In the VM, recording starts at boot (an AutoLogger session, set up before a restart), so boot and sign-in are in the trace. The ARM64 runner can't restart, so there it starts with the step, and Explorer and the shell's hosts (Start, Search, ShellHost for Quick Settings and the notification center, TextInputHost for the emoji panel) are restarted so that their startup is in the trace too: their flyouts check few features when they open. Process start events (`Microsoft-Windows-Kernel-Process`) give the processes' names.
2. Windows is left alone for 5 minutes (counted from sign-in in the VM), for background work and the tasks that run after sign-in.
3. Then, in the signed-in user's session, it opens one target at a time and closes it again a few seconds later: parts of the shell through their keyboard shortcuts (Start, Search, Quick Settings, the notification center, Widgets, Task view, the Win+X menu, clipboard history, the emoji panel, a new virtual desktop and others), the Start menu's apps that come with Windows, and every `ms-settings:` page, Windows Security page, Control Panel task link and shell folder Super God Mode found. It runs elevated (and the VM elevates administrators without asking, as the runner does), so nothing waits for a UAC prompt, and leaves out what would lock the PC or take over input (Narrator, Magnifier, Voice access, the On-Screen Keyboard). It stops opening targets after 75 minutes. From the time each kind of target took in the tests (about 5 to 6 seconds each, apps about 10), all of them should take about 75; no test has opened them all yet.
4. `tracerpt` decodes the trace and `summarize-trace.py` summarizes it in `trace.json`.

A trace adds about an hour and a half to a scan. Setting the repository variable `FEATURE_TRACE` to `false` leaves it out of both workflows.

A target's checks are those made while it was open by processes in the user's session, other than the script's own. Checks that most targets of a kind make (Settings' for any page, File Explorer's for any folder), and those a program makes whenever it starts (such as Settings, which some Control Panel links open), are left out, so what's left is particular to the target.

What a trace adds to a build's data (`update-data.py --trace`):

- Each feature it saw checked gets a `trace` entry: the stages its checks reported, the one most of them reported first (it's the stage compiled into the binary that made the check, and binaries can differ), how they came out (`on`, `off`), the variants of variant checks, and up to 8 of the processes and of the targets that checked it.
- A default where the symbols give none (`"defaultSource": "trace"`), and `alwaysEnabled` (or `alwaysDisabled`) where the symbols say enabled (disabled) but every check reported always: C++ code only shows whether a feature is enabled or disabled. Where the trace and the symbols disagree otherwise, the symbols' default stays, and the site shows what the trace saw next to it: the binaries that checked the feature aren't always the ones its default comes from.
- Features no binary's symbols and no feature store have, such as those of binaries Microsoft publishes no symbols for (`sppsvc.exe`) and of Store apps (Widgets). A trace isn't a list of what a build added, so these count in neither first seen nor the added and removed features of a comparison, and defaults from traces aren't compared between builds.
- The build's `trace.json`: the run (when, how long, the checks and events lost, the targets of each kind opened) and every target with the features put down to it.

On the site, a build's *Has runtime details* filter lists the features its trace saw, a feature's panel says what the trace saw of it, and searching for a target (such as `ms-settings:display` or `Task view`) finds the features checked when it was opened. In a build whose trace didn't see a feature, or that has no trace, the feature's panel shows where the newest trace that saw it saw it used: the processes and targets, with that build. Not its stages or results, which belong to that build (features' default stages change from one build to the next), so older builds don't need tracing for this.

In a 42-minute test on the ARM64 runner (26200.9974: the shell, the apps, every Settings and Windows Security page, and the first Control Panel links before the time limit), 2,034 features were checked. For 1,455 of them the default matched the symbols'; 246 had none (220 of them with code the symbols have), 213 that the symbols call enabled were always enabled, 43 disagreed, and 77 weren't in the build's data at all. 1,633 could be put down to at least one target. In a 16-minute test in the VM (26300.9974, Microsoft's image as it is, traced from boot, with the shell, the apps and the first Settings pages), 2,940 features were checked, 1,254 of them first while Windows started and 649 at sign-in; 134 were in no scanned build's data at all, most of them checked by Widgets, Start and the touch keyboard and emoji panel host, whose symbols the scans don't read. With nothing started before the trace, the shell's flyouts checked more there too: the Win+X menu 183 features, the notification center 157, Quick Settings 62.

A scan of the build again adds to what earlier traces saw. A trace can't see code for hardware the machine doesn't have (pen, touch, NPU, cameras, a battery), code that only runs when a feature that's off is on, code that depends on something other than features (region, edition, a Microsoft account), the setup screens, upgrades and most error paths. Kernel-mode code and processes that don't load `kernelbase.dll` probably write no events.

## What the code reveals

Every feature a binary uses comes with WIL plumbing compiled into it: a descriptor, state variables and small functions specific to that feature. `scan-symbols.py` decodes each such binary's ARM64 or x64 code and finds every call to those functions and every use of those variables, and the PDB's public symbols name the functions they're in. From that:

- **Callers:** the functions that check the feature (e.g. `CLogonTaskFramework::s_ShellHandwritingMethod`), which often say what it does even when the feature has no name.
- **Hints:** the strings, source file paths, imported functions, named data (registry values, WNF state names, ...) and other functions used by the first few of those callers.
- **Dependencies:** features that only work when other features are also on. C-style descriptors list them; C++ features check them inside their own plumbing. Some of the most-required features are named like monthly release gates (`Standalone_26_09_NonSec`), which hints at the update a feature belongs to.
- **Default state and change time:** whether a feature is on when nothing configures it, and when a change takes effect (on read, on reload, at sign-in or after a reboot). C-style descriptors store both; for C++ features they're read from the code of the feature's `GetCurrentFeatureEnabledState`. In testing on ARM64, the result agreed with the feature store's ImageDefault entries for all 1,301 features that had one. x64 code arranges that decision in more ways, so the x64 analysis follows the function's code with each possible configured state and sees which one sets the feature's 'enabled' bit. Features a binary only uses, while another binary defines them, get no default from it.
- **Lookup tables:** a function that references many features (such as KernelBase's `GetFeatureDescriptor`, which lists about 1,300) is a table, not a check, and is reported separately.

ARM64 and x64 code is decoded (ARM64X and ARM64EC binaries contain both); 32-bit binaries get no usage details. Callers and hints are found automatically and can include unrelated code from the same function. A function with no public symbol shows up as `(unnamed function after <nearest named function>)`.

## Data

```
data/
├── index.json                  Every scanned build with summary counts
├── symbol-cache.json           What each scanned PDB contained (by PDB name and GUID), reused by later scans
├── symbol-cache-AMD64.json     The same for the x64 scans
├── first-seen.json             First tracked build each feature ID appeared in (a list when several came out that day), by release date, per architecture
├── releases.json               Every build Microsoft has released for each serviced Windows 11 version (the site lists the newest six), and the newest of each Insider channel
├── builds/<build>-<arch>/      A folder per scanned build:
│   ├── features.json           The build's update, release date and KB, then all its feature IDs, one per line: id, name (null if unknown), modules, default state, requirements, feature store state
│   ├── details.json            What each binary's code reveals about each feature, one per line (callers, strings, ...)
│   ├── symbols.json            The build's PDBs, one per line, with what's needed to download their binaries, and which ones its scan didn't get (for the symbol catch-up)
│   ├── super-god-mode/         Super God Mode's statistics for the build: its CSV and XML files as it writes them, and run.json
│   └── trace.json              The build's latest feature trace: the run, and the features each target it opened checked
└── diffs/<old>_to_<new>.json   Changes between consecutive builds (.md versions for reading on GitHub)
```

Every feature ID found is listed, named or not. Many features only have a number for a name in the symbols (the ID itself, or an obfuscated hash); those have `"name": null` and keep the raw symbol names in `symbolNames`. A feature whose code has been removed from every binary can still be configured in the feature store; it keeps the name an earlier build found for it (`"nameSource": "earlierBuild"`). A feature that ViVeTool's dictionary names differently from the symbols also has that name, as `viveToolName`. "First seen" counts builds in the order they came out (by release date), so a feature in an Insider build counts there, not in the released build with a lower number that gets it later. Builds that came out the same day count together: a feature that several of them were the first to have, such as a security update's builds of 24H2, 25H2 and 26H2, lists them all. For the first tracked build, and for the first build scanned of each Insider channel (for the features no earlier build had), it only means the feature existed at least that early; the site marks these with an info icon. A build scanned in the VM can have `notes`, such as Store apps the VM couldn't update, and an Insider build has its `insiderChannel`. A build whose scan didn't get the symbols of 25 or more binaries that had features in earlier versions has `symbolsPending`: how many such binaries, how many of its features are only known from those earlier versions (`"unverified"`), and until when the symbol catch-up asks for them. Every scan has a few, such as Store apps updated to versions whose symbols Microsoft hasn't published; their features are only marked unverified. `symbolsUpdated` is the last time it added some.

`modules` lists the binaries that contain a feature's code. Some binaries ship full PDBs whose type information declares the IDs of hundreds of features they never use (the PDB of Windows.UI.Xaml.dll declares 1,878 feature IDs; the binary uses 55); those are listed separately in `declaredIn`. Where known, a feature also has `default` (`enabled`, `disabled`, `alwaysEnabled` or `alwaysDisabled`; `"defaultSource": "trace"` when it's from a feature trace), `changeTime` (`read`, `moduleReload`, `session` or `reboot`) and `requires` (feature IDs). A feature a [feature trace](#feature-traces) saw checked has `trace`, and the build's header has a summary of the trace, `trace`. The bulkier details are in each build's `details.json`.

The site doesn't load the `details.json` files or the `super-god-mode/` folders themselves. When it's published, `build-site-data.py` derives the files it loads: each feature's details from the newest build that has them, split into 64 files by feature ID so that a feature's panel downloads one small file instead of a build's whole details, and each build's Super God Mode CSV files in one JSON file, so that comparing two builds loads two files. That file also has the entries of the Settings app's search index (`Settings_XML_Resolved.xml`): each entry's description, page, deep link and keywords, and the feature that shows or hides it. Those derived files only exist on the published site, not in the repository.

## Running locally

`python scan-symbols.py` works on any Windows machine with Python 3 (no packages needed). It writes `extracted-names.txt` (`ID Name`) and `symbol-features.json`. See `--help` for options such as `--root`, `--symbol-cache` and `--keep-pdbs`.

To view the site locally, put the contents of `site/` and a copy of `data/` in a folder, run `python build-site-data.py --out <folder>/derived`, and serve the folder with any web server (`python -m http.server`).
