# Windows-Feature-ID-Scanner
A modern take on mach2's feature scanning: GitHub Actions scans Windows 11 for feature IDs and their names (ARM64 on a GitHub runner, x64 in a virtual machine built from Microsoft's servers), stores the results per build, and tracks what changes between builds.

**Browse the data:** the GitHub Pages site (published from `site/`) compares any two scanned builds (added / removed / renamed features, feature store changes, default state changes, and the shell folders, settings pages, Settings search entries, URL protocols and other links Super God Mode found in each) and lists every feature ID in a build with the build it first appeared in. Unless *Allow any build* is checked in their lists, the compare view's pickers grey out, besides the other's build, the builds newer than the new build (the old build's picker) or older than the old build (the new build's). Released builds are told apart by build number, and Insider builds, whose numbers run ahead of the released builds' of their Windows core, by release date (two from the same day count as the same age). Between a released build and an Insider build, the build of the Insider channel that came out closest to the released build (the later one where two are as close, found in the list of Insider releases, which also has the builds that weren't scanned) counts as the channel's first build newer than it: the channel's earlier builds are older than the released build, and that one and its later builds newer. 26H1, a separate Windows core whose build numbers (28000) are higher than those of 24H2, 25H2 and 26H2, counts as such a channel next to their builds (from the list of its releases), and the pickers list it below 26H2, as the list of released builds does; the site opens on the newest build of the newest version by name (26H2's). Click a feature to see what its code reveals: the functions that check it, the strings they use, its default state, and the chain of features it requires with their default states (a feature that's on by default stays off if one of them is off), with a button that copies its ID and theirs as a list for ViVeTool, and, where a feature trace saw it checked while Windows ran, the processes that checked it and the pages, folders or apps it was checked for. It also lists the builds Microsoft has released for every Windows 11 version and Insider channel, and which of them have been scanned. For x64 builds, the comparison also covers what the builds' files hold besides code (see [Resource data](#resource-data)): icons, UI text, APIs, font glyphs, policies, the shell's UI files and registry keys.

## How it works

The `Windows Feature Scanner` workflow (`.github/workflows/windows-scanner.yml`) runs on the `windows-11-arm` runner, because the Windows Server images don't carry the consumer feature set. Its steps, each a script in `scripts/`:

1. **`scan-symbols.py`** finds feature names and IDs in Microsoft's public symbols. For every binary under the Windows directories it downloads the matching PDB from the Microsoft symbol server and reads the symbols that WIL feature staging emits (`Feature_<Name>__descriptor`, `Feature_<Name>__private_descriptor`, `__WilFeatureTraits_Feature_<Name>::id`), then reads each feature's ID from the binary. C++ features in binaries built with older WIL have no descriptor; their ID comes from the code of their `GetCurrentFeatureEnabledState`, which passes it to Windows. This replaces mach2, which is retired and fails on current PDBs. For binaries that contain features, it also analyzes their code (see below). It also scans the binaries of the component store (WinSxS), the newest version of each component (`--component-store`): the files of optional features that aren't turned on, such as Hyper-V and the Windows Subsystem for Linux, of components that only live there, such as the servicing stack, and of installed ones outside the folders above, such as the driver store's drivers for hardware the machine doesn't have. Binaries already found in those folders are the same files, so their PDBs aren't read twice. Windows keeps the files of components that aren't installed compressed (LZMS blocks, or a delta against nothing); they're expanded with Windows' own `cabinet.dll` and `msdelta.dll`. A build lists the modules only the component store has in `componentStore`, and the site says so in a feature's details.
2. **`scan-features.ps1`** runs ViVeTool to dump the feature store (the IDs actually configured on the machine) and fills in names from step 1.
3. **`run-super-god-mode.ps1`** runs the latest release of [Super God Mode](https://github.com/ThioJoe/Windows-Super-God-Mode) and keeps its statistics: CSV files listing the build's CLSID shell folders, named special folders, task links, `ms-settings:` pages, deep links, URL protocols and hidden app links, and the XML data the task links and deep links come from. The shortcuts it creates aren't kept. If it fails, the scan carries on without its statistics.
4. **`trace-features.ps1`** records which features Windows' code checks while it runs, while it opens the shell's UI, the Start menu's apps and the pages and folders Super God Mode found (see [Feature traces](#feature-traces)). If it fails, the scan carries on without a trace.
5. **`update-data.py`** puts all of it in the build's folder, `data/builds/<build>-<arch>/`, with the update the build came in (e.g. 2026-08 B), its release date and KB article from the list of released builds, and regenerates the index, first-seen table and diffs. The workflow commits the result and republishes the site.

The workflow runs daily: a small check job reads the runner's Windows build and only starts a full scan when that build isn't in `data/` yet. It can also be started manually from the Actions tab, which always scans.

Scanning downloads several GB of PDBs (each is deleted after reading). What was found in each PDB is stored in `data/symbol-cache.json` (`data/symbol-cache-AMD64.json` for the x64 scans), keyed by the PDB's name and GUID, so later scans only download PDBs for binaries that changed. PDBs the symbol server doesn't have (404) are remembered too and re-checked after 14 days. The cache keeps the PDBs that builds still need: those of the builds the symbol catch-up still checks (see below) and those of the newest build of each base build number, so Insider builds, which have thousands of PDBs no other build has, don't keep making it bigger. If a changed binary's PDB still can't be downloaded after retries, or the symbol server doesn't have it (Microsoft can publish an update's symbols days after the update), the scan uses what the newest earlier version of that binary contained and marks those features `"unverified"`, rather than dropping them. Earlier means from that build or one before it, by the first build each PDB in the cache was seen in, so a released build never gets an Insider build's newer code this way. A PDB that was read before keeps its features even if it can't be downloaded again. Scanning a build again adds to its data and never removes anything: a feature, name, module, code detail or feature store configuration that only the earlier scan found is kept (symbols that can't be downloaded any more, a Store app version the new VM doesn't have, a feature store entry that isn't there today), and where both scans have a value, the new one is kept. The exception is a feature marked unverified, known only from an earlier version of a binary: it's replaced by what the binary's own symbols say once a scan reads them. Super God Mode statistics are replaced too, unless the new run produced none.

Microsoft can publish an update's symbols days after the update: the x64 symbols of most binaries KB5132061 changed went up three days after its release, after the VM had scanned its builds. So each scan also lists the build's PDBs in its folder (`symbols.json`), each with what's needed to download its binaries from the symbol server, which keeps binaries by file name, PE timestamp and image size, and marks the ones it got no verified data for. With every binary listed, a build's symbol data can also be made again later without a VM, for example after a change to the analysis. Every day, the `Symbol Catch-up` workflow (`.github/workflows/symbol-catch-up.yml`, `catch-up-symbols.py`) asks the symbol server for those PDBs, for 60 days after a build's release (14 for an Insider build, which the channel's next build replaces). When it has some of them now, a Windows runner scans them without a VM (`scan-symbols.py --manifest`: their binaries come from the symbol server by name, PE timestamp and image size, which for Windows' binaries is a hash of the compiled file rather than a date, and have to name the PDB in their debug record; the symbol server's copy of a binary can be signed differently from the build's, or not at all) and adds them to the build with `update-data.py`, which keeps the build's feature store data and Super God Mode statistics. Until then, the site shows a notice on the build and its comparisons, and a scan that didn't get the symbols of more than a few binaries with features gets a warning on its run.

## x64 builds in a virtual machine

The `Windows VM Feature Scanner` workflow (`.github/workflows/windows-vm-scanner.yml`) scans x64 builds of Windows 11 regardless of what runner images exist. GitHub's x64 runners run Windows Server, but they can run Hyper-V virtual machines, so `scan-in-vm.ps1` builds a Windows 11 Enterprise VM on one, entirely from Microsoft's servers:

1. The base image comes from the Media Creation Tool's catalogs of Windows images, which list each image file on Microsoft's servers with its hash. The tool's download link still points to a 24H2 catalog from June 2025; the tool then asks Windows Update's metadata service for the current catalog (26H2 at the time of writing), and so does the script. It also reads 24H2's catalogs of September and October 2024, which Microsoft still has (images of 26100.1742, the build 24H2 came out with for all PCs, and 26100.2033), so that 24H2 builds older than June 2025 can be scanned; nothing older than 26100.1742 can, since an update can't take a newer image back. It takes the newest image that can become the target version: a 26H2 image can't become 25H2, so 25H2 and 24H2 start from the 24H2 one. The image is applied to a virtual disk that boots without the setup screens. The catalogs have no image of 26H1, a separate Windows core for new devices. Its VM starts from the installation image of the whole build Windows Update gives a device in Release Preview 26H1 (the version's newest build, fetched as an Insider build is, see below), which is 26H1's base build, 28000.1, so any 26H1 build can be made from it with its cumulative update from the Update Catalog, which has 26H1's with no checkpoint updates. It's made as an Insider build's VM is (the Pro image with the files it refers to, made Enterprise, with the apps the edition comes with), without the update's packages; the build is signed for release, so flight signing stays off. The update has no app packages, though (Windows Update only offers 26H1 as a cumulative update, to 26H1 devices, which have their apps), so the apps come from the build Windows Update gives the Beta (26H1) channel, the same core's: the Store's packages, which the Store then updates as on any PC. The build's data notes it. 26H1 has no enablement package.
2. The target cumulative update, from the Microsoft Update Catalog, is installed inside the running VM with DISM. 24H2, 25H2 and 26H2 share their code and their cumulative updates.
3. Unless the image is that version already, the target version's enablement package is installed, which is what makes the build a 25H2 or 26H2 one. Microsoft distributes it only through Windows Update and WSUS, not the Update Catalog. WSUS has given the same file every time (`Windows11.0-KB5054156-x64.cab` for 25H2, `Windows11.0-KB5121794-x64.cab` for 26H2), so the script downloads it from that link, checked against its size and the SHA-1 its name ends with, and only asks WSUS when that fails or for a version it has no link for. The runner is a Windows Server, so it sets up the WSUS role in the background and synchronizes Windows 11's upgrades, which gives the package's file on Microsoft's servers; the VM installs that file alone with DISM, which keeps the build at the target update. Failing that, the VM takes the file from Windows Update's offer of the version (chosen with its target release version policy), which it only downloads, since the offer comes with the newest cumulative update. Windows Update doesn't offer the version every time; the VM then gets the file with the newest update installed, and goes back to a checkpoint taken before. That's what lets any past build be scanned, not only the newest.
4. Windows Update then installs whatever else it offers, as it would on any PC at that build (Defender and Windows Security platform updates, .NET and so on), leaving out updates that would change the build. The Microsoft Store updates the apps that come with Windows, which cumulative updates don't touch, so they're at the versions a PC gets today rather than the ones the image was made with. An app update that fails because the app is running is retried after closing what Windows' deployment log names, and whatever still fails is retried after a restart. Apps and these other updates don't decide the build, so one that still can't be installed doesn't stop the scan; the build's data gets a `notes` entry saying so.
5. After a last restart, the VM is checked against what the build is supposed to be:
   - Windows' servicing lists the build's cumulative update as installed, with no update half installed or waiting for a restart. (Microsoft's 26H2 image, 26300.9974, has Windows' servicing show a restart pending from the VM's first start on, which no restart clears and a cumulative update's restart does. Until something is installed with DISM, the restarts and this check don't count it, so a build can be scanned from its own image.)
   - `DISM /ScanHealth` and `sfc /verifyonly` find no file that differs from the component manifests Microsoft signs. (sfc's check of deployed drivers flags `bthmodem.sys` in Microsoft's 24H2 image of September 2024, whose copy in `System32\drivers`, 26100.1, is older than its driver package, updated in the image to 26100.1301. A file sfc flags only that way, and that is exactly as in the image, doesn't count.)
   - `verify-windows-files.py` checks the installed files against Microsoft's own lists. Each update's KB article (read through the Microsoft Learn API, see below) links a file list with the name, version and SHA-256 of every file the update carries. (The lists of updates from before 2026 have no hashes. Files are then matched by name and size, and a file such a list doesn't name, such as a listed binary's language resources or a file installed under another name, is left to the checks above.) Every file installed from Windows' component store has to be either a file one of the installed updates lists (by SHA-256) or exactly the file in Microsoft's image the VM started from, listed before Windows first starts (26H1's image from Windows Update once it's made Enterprise with its apps, see step 1). Which of an update's components apply to a system is decided by Windows' servicing, which the first check covers.

   If a check fails, nothing is recorded. The reports (`verification.json` and the others, plus a list of every file with its SHA-256) are kept with the run's artifacts either way.
6. The same scan as on the ARM64 runner runs inside the VM, with Super God Mode run as the VM's own user, as it would be by someone using that PC. If the VM didn't end up at the expected build, nothing is recorded. Then the VM restarts for the feature trace, which records from boot on, so boot and sign-in are in it.
7. Windows shuts down, and `scan-resources.py` reads the VM's disk on the runner (see [Resource data](#resource-data)).

Each download logs its size and how long it took. A 26H2 base image a scan downloads is saved in the repository's Actions cache, and later scans of 26H2 builds start from it (after checking its hash against the catalog's); only the 26H2 image, since it and the 24H2 one together wouldn't fit in the cache's 10 GB. In practice the runners download the images from Microsoft in about a minute (4.3 GB in 44 to 78 seconds, 5.8 GB in 33 to 82 seconds), and restoring the 5.8 GB image from the cache took 87 seconds (64 to download it at about 95 MB/s, 22 to unpack it), so the cache saves no time; saving it took about two and a half minutes. It's kept in case downloading from Microsoft is slow or fails.

Starting from an older image and updating it gives the same Windows as Microsoft's own image of that build: built both ways (from Microsoft's 26300.9711 image as it is, and from the June 2025 24H2 image plus the October update and the 26H2 enablement package), every file installed from the component store was byte-identical between the two VMs, and neither had one the other lacked, apart from three of .NET's precompiled native images. The differences were in apps (the Store apps and Edge an image comes with), the update history, and files Windows generates on each PC.

A daily check (`check-windows-builds.py`) finds the builds Microsoft has released for every Windows 11 version and every Windows Insider channel. It starts a scan for each build of 26H2, 26H1, 25H2 and 24H2 (the versions the VM can be built for) that is newer than the newest build of that version in `data/`, so no build is missed when two come out between checks (the newest three, if more are missing). A version with no build in `data/` yet starts at its newest. It also starts a scan for the newest build of each Insider channel except Release Preview (see below), unless the repository variable `INSIDER_SCANS` is `false`. Monthly security updates, optional previews and out-of-band releases all count, since each is a different build. The sources are Microsoft's, read on every check and compared with each other:

- **Versions and their updates:** support.microsoft.com's index of its Windows 11 update history (JSON), checked against the [Windows 11 release information](https://learn.microsoft.com/en-us/windows/release-health/windows11-release-information) page, which also stands in for the index when that can't be read.
- **Insider builds:** the index of the [Windows Insider release notes](https://learn.microsoft.com/en-us/windows-insider/) (JSON), with each build's release date from [Flight Hub](https://learn.microsoft.com/en-us/windows-insider/flight-hub/), which also stands in for the index. And Windows Update itself (`windows_update.py`, as below): the build it gives each channel except Release Preview's, with its release date, the day its update was published (the `LastChangeTime` of the update's deployment, which is Flight Hub's date wherever both have the build). A build the release notes don't list, such as 29712.1013 while they had 29712.1000, is listed with that date (and stays listed while they don't list it, as their older builds do), and a listed build Flight Hub has no date for gets it.
- **Pages:** KB articles, the release information page and Flight Hub are read through the [Microsoft Learn API](https://learn.microsoft.com/api/mcp) (`microsoft_learn.py`), which gives a page as Markdown. A page's HTML is only read when that fails.

The builds a run scans are scanned at the same time, each on its own runner. Once they've all finished or failed, one job adds the ones that were scanned to `data/` in a single commit, oldest first (a build's missing feature names are filled in from earlier builds, including in builds already in `data/` when an earlier build is added after them), and merges their symbol caches (`merge-symbol-caches.py`), keeping usage details for the PDBs of the builds it scanned as far as the file stays under 90 MB (GitHub refuses files over 100 MB).

A source that fails, or two that disagree, show up as warnings on the run. The run's summary lists the newest builds of every version and channel; the list is kept in `data/releases.json` and shown on the site. 26H1, a separate Windows core for new devices, is scanned too, though the Media Creation Tool's catalogs have no image of it (see step 1 of the VM above).

Insider builds are scanned in the VM too. Windows Update gives an Insider channel's newest build to a request that describes a device in that channel, without anything being enrolled or signed in. `windows_update.py` makes the requests Windows' own update client makes (Microsoft's Windows Update protocol: `GetCookie`, `SyncUpdates`, `GetExtendedUpdateInfo2`) and gets the update's files, each checked against the SHA-256 in its metadata. The update is the whole build, in every language and edition (about 100 GB), and its `AggregatedMetadata.cab` has the component databases that say what each file is. A released build's image can't be updated to an Insider build: the channels' cumulative updates are built on the channels' own baseline (`ge_release_flt` 26100.6, not 26100.1), which is why Microsoft's docs say a device joins a channel by an in-place upgrade. So for `scan-in-vm.ps1 -InsiderChannel <channel>`, the VM is made from the build's own installation image instead of the Media Creation Tool's: the Pro image (`professional_en-us.esd`), applied with DISM together with the files it refers to (in the update's package ESDs and WIMs, and in the cabs of the features an installation has, unpacked with `expand.exe` and captured into one WIM), then made Enterprise with `DISM /Set-Edition`. The apps that come with Windows are separate packages in the update: the ones the edition's component database names (for Pro, 47 in the Beta and Experimental builds, the same apps the Media Creation Tool's Enterprise image has, and 50 in the 26H1 and Future Platforms builds) are provisioned in the image with DISM, each with the frameworks it requires and its license from the app database (`DesktopTargetCompDB_App_Neutral`). The VM then installs the build's cumulative update, the checkpoint cumulative update it builds on, the enablement package that gives the build the channel's build number, and the .NET Framework update, with DISM. A Future Platforms update's metadata names no cumulative update: when the update has a KB, the `.msu` of that KB is its cumulative update (29712.1013's image is 29712.1000, and KB5136956 makes it 29712.1013); without one, the update is a whole build, its image is the build already, and only the .NET Framework update is installed, if the update has one. Windows Update can give a newer revision of a channel's build before the release notes list it (29712.1013 while they had 29712.1000): the VM then scans the revision it gets, and the daily check counts it as the channel's build. Insider builds are signed with Microsoft's development certificates, so flight signing is on, as on any Insider PC and as Microsoft documents for Insider builds (`bcdedit /set flightsigning on`); nothing else about the VM is changed, and it isn't enrolled in the program. The checks then run without the file check, since Insider builds have no file lists. After its first start, a Future Platforms build runs eBPF's files (`ebpfapi.dll` and five others) as the `_preview` variants it has next to them, which sfc reports as different from the component store; the check accepts a file that's the same as its `_preview` variant, when sfc doesn't flag that variant. This has been tried with Beta, Experimental, Experimental (26H1) and Experimental (Future Platforms). Windows Update only gives a channel's newest build, so that's the one the daily check scans: a build that comes out and is replaced between two checks isn't scanned. Release Preview's builds are scanned as the updates they become.

A scan of one build takes about an hour to an hour and a half on GitHub's runner. Since 25H2 and 26H2 start from different images, a comparison between them can also show differences in the apps the images come with: the Store doesn't bring every app on an older image to the version a newer image has. Manual runs can pick the versions, scan specific builds (older ones, for example) and rescan builds that are already in `data/`. (Microsoft's ISO download page turns away requests from GitHub's runners, so the base image comes from the Media Creation Tool's catalog instead.)

## Feature traces

Each time Windows' code checks a feature, Windows can write an event: the `Microsoft-Windows-FeatureConfiguration` ETW provider (`{c2f36562-a1e4-4bc3-a6f6-01a7adb643e8}`, with its manifest in `fcon.dll`) has an event for each stage a feature can be compiled with (1007 always disabled, 1008 disabled by default, 1009 enabled by default, 1010 always enabled), which gives the feature's ID and how the check came out (its `Kind`: on or off, and the variant of a variant check, as Microsoft's own StagingTool decodes it). The event header gives the process. A feature only shows up if code that checks it runs while the trace records, so `trace-features.ps1` makes Windows run as much of that code as it can:

1. In the VM, recording starts at boot (an AutoLogger session, set up before a restart), so boot and sign-in are in the trace. The ARM64 runner can't restart, so there it starts with the step, and Explorer and the shell's hosts (Start, Search, ShellHost for Quick Settings and the notification center, TextInputHost for the emoji panel) are restarted so that their startup is in the trace too: their flyouts check few features when they open. Process start events (`Microsoft-Windows-Kernel-Process`) give the processes' names.
2. Windows is left alone for 5 minutes (counted from sign-in in the VM), for background work and the tasks that run after sign-in.
3. Then, in the signed-in user's session, it opens one target at a time and closes it again a few seconds later: parts of the shell through their keyboard shortcuts (Start, Search, Quick Settings, the notification center, Widgets, Task view, the Win+X menu, clipboard history, the emoji panel, a new virtual desktop and others), the Start menu's apps that come with Windows, and every `ms-settings:` page, Windows Security page, Control Panel task link and shell folder Super God Mode found. It runs elevated (and the VM elevates administrators without asking, as the runner does), so nothing waits for a UAC prompt, and leaves out what would lock the PC or take over input (Narrator, Magnifier, Voice access, the On-Screen Keyboard). It stops opening targets after 90 minutes, a limit for a target that hangs. In a test on the ARM64 runner all 814 took 68 minutes: about 3.5 seconds for a Settings or Windows Security page, 4.5 for a folder, 5.5 for a Control Panel link and 9.5 for an app. On that runner, Settings stopped responding each time it was sent to another page from Display or Advanced display (from Display even after 15 seconds on it): Windows gives up on the page after a minute, so after 10 seconds the script closes Settings, starts it again and opens the page again.
4. `tracerpt` decodes the trace and `summarize-trace.py` summarizes it in `trace.json`.

A trace adds about an hour and ten minutes to a scan. Setting the repository variable `FEATURE_TRACE` to `false` leaves it out of both workflows. A build scanned without a trace can get one without being scanned again: run the VM workflow with *trace_only* and the builds in *builds*. The VM is made and updated the same way, then only Super God Mode (whose pages and links the trace opens) and the trace run (`scan-in-vm.ps1 -TraceOnly`), and `update-data.py` adds the trace to the build's data and leaves the rest of it as it was. The builds have to be in `data/`, and an Insider build has to be its channel's newest, as for a scan.

A target's checks are those made while it was open by processes in the user's session, other than the script's own and, on a GitHub runner, the runner's (its agent starts `wsl.exe` in the user's session every 30 seconds). Checks that most targets of a kind make (Settings' for any page, File Explorer's for any folder), and those a program makes whenever it starts (such as Settings, which some Control Panel links open), are left out, so what's left is particular to the target. A target that failed to open (such as a Control Panel link to a program the image doesn't have) has none: while it was open, Windows only did other things.

What a trace adds to a build's data (`update-data.py --trace`):

- Each feature it saw checked gets a `trace` entry: the stages its checks reported, the one most of them reported first (it's the stage compiled into the binary that made the check, and binaries can differ), how they came out (`on`, `off`), the variants of variant checks, and up to 8 of the processes that checked it (the most checks first) and of the targets it was checked on (those with the fewest features first, the most particular to it). A target is named by what was opened, which is the same in every language, between backticks, then its name: a Settings or Windows Security page by its address (`` `ms-settings:about` ``), an app by its program or app ID (``App: `odbcad32.exe` "ODBC Data Sources (64-bit)"``, ``App: `Microsoft.WindowsCalculator_8wekyb3d8bbwe!App` "Calculator"``), a folder by its `shell:` address (``CLSID Folder: `shell:::{00021400-…}` (Desktop)``, ``Named Folder: `shell:AccountPictures` ``), a hotkey by its keys (``Hotkey: `Win+S` (Search)``), and the shell's restart by its program (``Upon App Relaunch: `explorer.exe` ``). A Control Panel link is named by its name alone (`Control Panel: "Backup and Restore (Windows 7)"`), since its command can be long, except where links of the same name run different programs: then each has its program first (``Control Panel: `netplwiz.exe` "Change account type"``), so that a label names one thing in the build. The build's `trace.json` has every target's app ID or command.
- A default where the symbols give none (`"defaultSource": "trace"`), and `alwaysEnabled` (or `alwaysDisabled`) where the symbols say enabled (disabled) but every check reported always (`"symbolDefault"` keeps the symbols' value): C++ code only shows whether a feature is enabled or disabled. Where the trace and the symbols disagree otherwise, the symbols' default stays, and the site shows what the trace saw next to it: the binaries that checked the feature aren't always the ones its default comes from.
- Features no binary's symbols and no feature store have, such as those of binaries Microsoft publishes no symbols for (`sppsvc.exe`) and of Store apps (Widgets). A trace isn't a list of what a build added, so these count in neither first seen nor the added and removed features of a comparison, and comparisons between builds compare the symbols' defaults, not the traces'.
- The build's `trace.json`: the run (when, how long, the checks and events lost, the targets of each kind opened) and every target with the features put down to it.

On the site, a build's *Has runtime details* filter lists the features its trace saw, a feature's panel shows what the trace saw of it under *Runtime trace data* (*Found usage by*: the processes that checked it; *Found triggers*: the targets it was checked on; *Feature runtime state*: how the checks came out, and whether that matches the default they reported, the stage compiled into the binary that made them), and searching for a target (such as `ms-settings:display` or `Task view`) finds the features checked when it was opened. In a build whose trace didn't see a feature, or that has no trace, the feature's panel shows where the newest trace that saw it saw it used, under *From other builds*: the processes and targets, with that build (a link to the feature there). Not its stages or results, which belong to that build (features' default stages change from one build to the next), so older builds don't need tracing for this.

In a 73-minute test on the ARM64 runner (26200.9974, with every target), 2,267 features were checked. For 1,661 of them the default matched the symbols'; 267 had none (258 of them with code the symbols have), 226 that the symbols call enabled were always enabled, 35 disagreed, and 78 weren't in the build's data at all, most of them checked by Start and the Windows Modules Installer (`TiWorker.exe`). 1,830 could be put down to at least one target. In a 16-minute test in the VM (26300.9974, Microsoft's image as it is, traced from boot, with the shell, the apps and the first Settings pages), 2,940 features were checked, 1,254 of them first while Windows started and 649 at sign-in; 134 were in no scanned build's data at all, most of them checked by Widgets (whose symbols Microsoft doesn't publish), Start and the touch keyboard and emoji panel host. With nothing started before the trace, the shell's flyouts checked more there too: the Win+X menu 183 features, the notification center 157, Quick Settings 62.

A scan of the build again adds to what earlier traces saw. A trace can't see code for hardware the machine doesn't have (pen, touch, NPU, cameras, a battery), code that only runs when a feature that's off is on, code that depends on something other than features (region, edition, a Microsoft account), the setup screens, upgrades and most error paths. Kernel-mode code and processes that don't load `kernelbase.dll` probably write no events.

## Resource data

Besides feature IDs, each x64 build's files are read for what they hold besides code, so that comparing two builds also shows changed icons, new UI text, new APIs and so on. `scan-resources.py` only reads files, so it runs on the runner against the VM's disk, mounted read-only once Windows has shut down (which also makes the registry hives and the scheduled tasks readable). It records, for every file version no earlier build had (files are identified by their SHA-256):

- **Executables** (DLL, EXE, SYS and the like, the `.mun` files in `SystemResources` that hold the resources of system binaries such as imageres and shell32, en-US `.mui` files, visual styles): the PE timestamp and image size (what the symbol server keeps a binary under), the file version, the exports, and a hash of every resource. From the resources: icons and cursors (each image converted to PNG where it isn't one already, named by the hash of the original), bitmaps and images, string and message tables, and dialog and menu text.
- **WinRT metadata** (`.winmd`): the types and their methods, properties, events and fields.
- **Fonts** (Segoe Fluent Icons, Segoe MDL2 Assets, Segoe UI Emoji, Segoe UI Variable): the files, a hash of each character's glyph (its outline, variations and color layers), and of each ligature, which is how emoji with skin tones and ZWJ sequences are drawn.
- **Cursors** (`Windows\Cursors`): each frame as PNG, with its hotspot, and animated cursors' timing.
- **Whole files:** the shell's UI files in `SystemApps`, `ShellExperiences`, `ImmersiveControlPanel`, `ShellComponents` and `SystemResources` (images, SVGs, Lottie animations and other JSON, the setup screens' and other web apps' HTML, JavaScript and CSS, compiled XAML, `.pri` files, videos), Group Policy templates, wallpapers and lock screens, sounds, themes, PowerShell's inbox modules, servicing package manifests (which list the optional features and capabilities) and scheduled tasks.
- **Registry** (the SOFTWARE and SYSTEM hives, read by the script itself): MDM/CSP policy definitions (`PolicyManager\default`), services and drivers, ETW providers and WinRT activatable classes.
- **Every file of the build**, with its size and hash, from the file check's list.

Store apps (`WindowsApps`), Edge and Copilot are left out: they update on their own schedule, not with builds.

Everything goes in the repository's `assets` branch, an orphan branch (no history shared with `main`), stored once and named by the first 16 hex digits of its SHA-256 (`<h>` is the first of them, `<hh>` the first two):

```
assets branch
├── icons/<W>x<H>/<h>/<hash>.png      Icon images (cursors/ and bitmaps/ the same way)
├── images/<W>x<H>/<h>/<hash>.<ext>   Other images (images/svg/<h>/<hash>.svg for SVGs)
├── files/<kind>/<h>/<hash><ext>      Whole files (fonts, shell, policies, sounds, themes, powershell, servicing, tasks)
├── meta/<hh>/<hash>.json             What was read from a file version: its name, timestamp, version and so on, and its parts' hashes
├── parts/<hh>/<hash>.json            Each part on its own (an executable's exports, icons, strings, ...), so that a part a new version of
│                                     a file has unchanged isn't stored again
├── registry/<hh>/<hash>.json         Each registry key recorded
└── builds/<build>-<arch>/
    ├── files.csv.gz                  Every file of the build: path, size, hash
    └── index.json.gz                 Each file the script read, with its hash, and for each file version the hashes of its parts
```

A scan writes only what the branch doesn't have yet (the scan job lists the branch's files first, without downloading them). The VM workflow's commit job adds the scans' new files to the branch (`merge-resources.py`) and pushes it before committing `data/`, where `data/builds/<build>-<arch>/resources.json` records that the build has resource data, which `update-data.py` copies into `data/index.json`. A build already in `data/` can get its resource data without being scanned again: run the VM workflow with *resources_only* and the builds in *builds* (`scan-in-vm.ps1 -ResourcesOnly`: the VM is made, updated and checked as for a scan, without the Store app updates, and only the resource data is read). An Insider build has to be its channel's newest, as for a scan: Windows Update only gives a channel's newest build.

On the site, comparing two builds that both have resource data adds a *Resource Data* section: icons (how many of an icon's variations, an image of one size and bit depth, changed, and in a row's details the old and new images of those that changed, lined up by size, with a box saying "none" where only one of them has a size, and how many didn't change; an image whose file differs but whose pixels are the same counts as unchanged, since a PNG can be compressed again with nothing in it changing, as Edge's icons in 26300.9711 were; an icon whose only image is 1×1 is left out where neither build has more than that, since programs built from Chromium's code, such as `copilotapp.exe`, keep a 1×1 image in the places of the icons they don't use, which Windows refers to by position), bitmaps and images in executables, UI text (strings, messages, dialogs and menu items), APIs (exports, WinRT types and members), font glyphs drawn with each build's own font file, whole files (with images shown and links to the files), registry keys, and every file added or removed (not counting Edge, Copilot and the Store apps, for the same reason). Files are matched across the two builds by their paths, without what changes in a folder's name when what's in it is updated: the hash in the name of a driver package's folder in the driver store, and the version in the names of the Windows Security platform's folder (Windows Update updates the platform on its own schedule) and the servicing stack's. The copies of the system apps' files in `Windows\SystemApps\Shared\<name>\<hash>\`, whose folder is named with a 64-digit hash that changes when the file does, are left out where the same build has the same file (the same hash) at another path, which is compared there; in every build with resource data, every copy has one, in an app's own folder. Matched by path, a changed file there was listed as removed and added again, a DLL with all its exports (IntentRecognizer.dll's 41 in 26320.10022). Registry values are compared the same way where they hold such paths, regardless of letter case and of the order of a list, and the values Windows writes as it runs are left out: times, counters and IDs it makes for the machine, network bindings, performance counter numbers, whether an ETW provider was ever enabled, WNF state names, and the processor and graphics power settings it registers as MDM/CSP knobs for the hardware it finds, which differ between runners. Bitmaps and images in executables whose files differ but whose pixels are the same are left out the same way. Which images have the same pixels as another is found when the site is published (`analyze-images.py`, which the site's workflow runs on the branch's image folders with Pillow, about 31,000 images in 20 seconds), as are the images that are almost all white (at least 90% of their visible pixels with a brightness of 245 or more), which the site shows on a darker checkerboard; both are in the derived `images.json`. The site reads it all from the branch through GitHub's raw file links, which other sites may read. A comparison reads about a thousand of them in 20 seconds, and GitHub answers HTTP 429 when one address reads too many in a short time (two comparisons in a row can do it), so the site waits and tries again, up to five times, longer each time.

The first build stores the most; after that, a build adds only what changed. A build has 23,000 to 28,000 files to read, which takes under a minute. (A test against a whole GitHub runner, with its Visual Studio and other tools, read 129,397 files in 13 minutes.)

## What the code reveals

Every feature a binary uses comes with WIL plumbing compiled into it: a descriptor, state variables and small functions specific to that feature. `scan-symbols.py` decodes each such binary's ARM64 or x64 code and finds every call to those functions and every use of those variables, and the PDB's public symbols name the functions they're in. From that:

- **Callers:** the functions that check the feature (e.g. `CLogonTaskFramework::s_ShellHandwritingMethod`), which often say what it does even when the feature has no name.
- **Hints:** the strings, source file paths, imported functions, named data (registry values, WNF state names, ...) and other functions used by the first few of those callers.
- **Dependencies:** features that only work when other features are also on. C-style descriptors list them; C++ features check them inside their own plumbing. Some of the most-required features are named like monthly release gates (`Standalone_26_09_NonSec`), which hints at the update a feature belongs to.
- **Default state and change time:** whether a feature is on when nothing configures it, and when a change takes effect (on read, on reload, at sign-in or after a reboot). C-style descriptors store both; for C++ features they're read from the code of the feature's `GetCurrentFeatureEnabledState`. In testing on ARM64, the result agreed with the feature store's ImageDefault entries for all 1,301 features that had one. x64 code arranges that decision in more ways, so the x64 analysis follows the function's code with each possible configured state and sees which one sets the feature's 'enabled' bit. Features a binary only uses, while another binary defines them, get no default from it.
- **Lookup tables:** a function that references many features (such as KernelBase's `GetFeatureDescriptor`, which lists about 1,300) is a table, not a check, and is reported separately.

ARM64 and x64 code is decoded (ARM64X and ARM64EC binaries contain both); 32-bit binaries get no usage details. Callers and hints are found automatically and can include unrelated code from the same function. A function with no public symbol shows up as `(unnamed function after <nearest named function>)`.

## Data

```
data/
├── index.json                  Every scanned build with summary counts
├── symbol-cache.json           What each scanned PDB contained (by PDB name and GUID), reused by later scans
├── symbol-cache-AMD64.json     The same for the x64 scans
├── first-seen.json             First tracked build each feature ID appeared in (a list when several came out that day), by release date, per architecture
├── releases.json               Every build Microsoft has released for each serviced Windows 11 version (the site lists the newest six), and the newest of each Insider channel
├── builds/<build>-<arch>/      A folder per scanned build:
│   ├── features.json           The build's update, release date and KB, then all its feature IDs, one per line: id, name (null if unknown), modules, default state, requirements, feature store state
│   ├── details.json            What each binary's code reveals about each feature, one per line (callers, strings, ...)
│   ├── symbols.json            The build's PDBs, one per line, with what's needed to download their binaries, and which ones its scan didn't get (for the symbol catch-up)
│   ├── super-god-mode/         Super God Mode's statistics for the build: its CSV and XML files as it writes them, and run.json
│   ├── trace.json              The build's latest feature trace: the run, and the features each target it opened checked
│   └── resources.json          That the build has resource data in the assets branch (see Resource data), with counts
└── diffs/<old>_to_<new>.json   Changes between consecutive builds (.md versions for reading on GitHub)
```

Every feature ID found is listed, named or not. Many features only have a number for a name in the symbols (the ID itself, or an obfuscated hash); those have `"name": null` and keep the raw symbol names in `symbolNames`. A feature whose code has been removed from every binary can still be configured in the feature store; it keeps the name an earlier build found for it (`"nameSource": "earlierBuild"`). The feature store entries Windows' rollout service writes (priority `Service (4)`, type `Experiment (1)`) stay in a build's data but count in neither first seen nor comparisons, where a feature only they have counts as absent: Windows writes them after it checks in with Microsoft, for features Microsoft is rolling out to a share of PCs or testing, so which ones a VM gets depends on the day and on chance (no features only they have in the 2024 and 2025 builds scanned on November 26, 2026, 74 in a September 2026 build scanned the same day, and 211 to 226 in the 24H2, 25H2 and 26H2 builds of July to November 2026 scanned November 18 to 20). A feature that ViVeTool's dictionary names differently from the symbols also has that name, as `viveToolName`. "First seen" counts builds in the order they came out (by release date), so a feature in an Insider build counts there, not in the released build with a lower number that gets it later. Builds that came out the same day count together: a feature that several of them were the first to have, such as a security update's builds of 24H2, 25H2 and 26H2, lists them all. For the first tracked build, and for the first build scanned of each Insider channel (for the features no earlier build had), it only means the feature existed at least that early; the site marks these with an info icon. A build scanned in the VM can have `notes`, such as Store apps the VM couldn't update, and an Insider build has its `insiderChannel`. A build whose scan didn't get the symbols of 25 or more binaries that had features in earlier versions has `symbolsPending`: how many such binaries, how many of its features are only known from those earlier versions (`"unverified"`), and until when the symbol catch-up asks for them. Every scan has a few, such as Store apps updated to versions whose symbols Microsoft hasn't published; their features are only marked unverified. `symbolsUpdated` is the last time it added some.

`modules` lists the binaries that contain a feature's code. Some binaries ship full PDBs whose type information declares the IDs of hundreds of features they never use (the PDB of Windows.UI.Xaml.dll declares 1,878 feature IDs; the binary uses 55); those are listed separately in `declaredIn`. Where known, a feature also has `default` (`enabled`, `disabled`, `alwaysEnabled` or `alwaysDisabled`; `"defaultSource": "trace"` when it's from a feature trace), `changeTime` (`read`, `moduleReload`, `session` or `reboot`) and `requires` (feature IDs). A feature a [feature trace](#feature-traces) saw checked has `trace`, and the build's header has a summary of the trace, `trace`. The bulkier details are in each build's `details.json`.

The site doesn't load the `details.json` files or the `super-god-mode/` folders themselves. When it's published, `build-site-data.py` derives the files it loads: each feature's details from the newest build that has them, split into 64 files by feature ID so that a feature's panel downloads one small file instead of a build's whole details, and each build's Super God Mode CSV files in one JSON file, so that comparing two builds loads two files. That file also has the entries of the Settings app's search index (`Settings_XML_Resolved.xml`): each entry's description, page, deep link and keywords, and the feature that shows or hides it. For each build with a feature trace, a last file has what its app and Control Panel targets opened in full (a program with its folder, a link's command), which a feature's panel shows on hovering the program or the link's name. `analyze-images.py` adds `images.json`, from the resource data's images (see Resource data). Those derived files only exist on the published site, not in the repository.

## Running locally

`python scripts/scan-symbols.py` works on any Windows machine with Python 3 (no packages needed). It writes `extracted-names.txt` (`ID Name`) and `symbol-features.json`. See `--help` for options such as `--root`, `--symbol-cache` and `--keep-pdbs`.

To view the site locally, put the contents of `site/` and a copy of `data/` in a folder, run `python scripts/build-site-data.py --out <folder>/derived`, and serve the folder with any web server (`python -m http.server`).
